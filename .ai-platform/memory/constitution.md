# TellPlot 项目章程

## Metadata

- Version: 0.5.0
- Status: Confirmed
- Last updated: 2026-07-29
- Approval: 用户已确认轻量基础图表库、框架无关编辑器核心与目标级交付方式

## Purpose

本章程定义 TellPlot 在产品边界、图表架构、数据正确性、交互质量和交付治理上的不可协商原则。

## Principles

### P-001 真实图表需求优先

新增图表和公共能力以明确使用需求为依据。未经验证的通用能力不得进入核心范围。

### P-002 原始数据与视图分离

原始金额、维度和来源关系保持不可变。排序、分组、折叠、注释和强调属于独立 `ViewSpec`。

### P-003 一个确定性编辑入口

图表直接操作、结构大纲、键盘和宿主命令使用同一套类型化命令。每条命令可校验、可撤销、可重放。

### P-004 轻量核心

TellPlot 只建设基础图表所需的数据、渲染、交互、配置和导出能力。核心不包含 AI、Agent、Dashboard、
服务端工作流或尚未证明价值的插件框架。

### P-005 数据不变量高于视觉效果

来源不丢失不重复、聚合准确、总额稳定和锁定规则是阻断性要求。动画不得掩盖正确性失败。

### P-006 G2 原生能力优先

G2 负责图形、场景边界、事件和动画。只有原生能力无法满足已确认需求时，才评估额外依赖；不得维护
第二套通用渲染或动画引擎。

### P-007 直接操作与精确操作并存

图表画布提供直观操作，结构大纲提供精确排序、层级编辑、键盘操作和可访问性入口。

### P-008 性能可感知、动作可打断

拖拽反馈跟随指针，提交动画短且可打断，并遵循 `prefers-reduced-motion`。

### P-009 实现后再抽象

共享边界必须由真实需求或至少两个宿主适配消费者证明。框架无关 editor runtime 由 imperative DOM、
React 与 Vue 三种已确认宿主合同共同约束；其他抽象不得由目录对称、未来猜测或扩展想象驱动。

### P-011 框架边界清晰

数据、命令、投影和完整编辑器 runtime 不依赖 React、Vue 或其他宿主 UI 框架。React/Vue 适配层只负责
生命周期、属性、事件和实例映射，不复制领域状态、G2 生命周期或编辑行为。

### P-010 Evidence over assertion

质量结论来自类型检查、单元测试、真实浏览器、可访问性、性能和图表输出证据。

## Testing And Quality

- 数据转换、命令和图表不变量默认采用 TDD。
- 核心用户流程具有真实浏览器测试。
- 拖拽、分组、折叠、撤销和导出覆盖失败、取消和恢复路径。
- 性能测试使用目标规模和真实 G2 图形，不以空图或纯 Mock 代替。
- 可访问性覆盖键盘路径、焦点反馈、状态播报和 reduced motion。
- 公共包验证 ESM、CJS、类型声明、imperative DOM、React、Vue 和浏览器兼容。

## Security And Privacy

- 核心包默认不发起网络请求。
- 日志、错误报告和性能指标不得包含金额、标签或来源明细。
- 宿主传入的数据只用于本地图表处理、编辑和导出。

## Dependency Policy

- 新依赖必须解决已确认问题，并说明替代方案、体积、维护状态、许可证和退出策略。
- G2 负责图表渲染及图形过渡。
- 框架无关 runtime 优先使用浏览器 Pointer Events、Keyboard Events 与 G2 事件，不引入宿主框架专属
  drag-and-drop 依赖。
- 不为“更丝滑”或未来扩展引入动画框架、状态框架或插件框架。

## Goal-Level Delivery

- 用户批准一个大目标的范围、不可变边界和最终验收标准。
- 每个目标可以包含多个内部任务、测试循环和修复步骤。
- 内部任务不设置逐项用户验收；执行方负责连续完成、复核和整合 evidence。
- 目标完成后统一进入 `Needs_Review`，由用户查看目标级成果并验收。
- breaking public API、schema、依赖、远程 Git、publish、release 和范围扩张始终保留独立人工闸门。

## Git And Review Policy

- `main` 保持可追溯、可构建的稳定历史。
- 不覆盖或回滚用户的无关工作。
- 未经明确授权，不执行 stage、commit、push、PR、merge、publish 或 release。
- 目标完成前执行 spec compliance、代码质量和 QA review；用户只接收合并后的目标级结论。

## Change Process

1. 产品范围、公共边界或原则变化写入 canonical artifacts。
2. 用户明确批准后才能进入目标执行。
3. 内部任务在已批准目标内连续推进。
4. 任何放宽本章程的例外必须说明范围、风险、验证和退出条件。
